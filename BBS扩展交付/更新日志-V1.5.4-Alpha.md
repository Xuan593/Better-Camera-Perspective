## V1.5.4-Alpha（2026-10-10）【实验版 · 修复「多样追踪」三大相机关键帧异常】

> 用户在多样追踪剪辑实测录屏中反馈三个相互关联的异常：① 第 1 帧建好关键帧、第 10 帧新建锚点帧并选定模型后，XYZ 三轴关键帧被**全部强制归零**（不是当前帧，是所有）；② 删除偏航帧后重新新建帧，方位大致正确但**数值天差地别**，播放时可能引发不明所以的极高角度水平视角切换；③ 两者结合的连锁故障：新建剪辑使用默认关键帧数值并选好模型后，XYZ 被强制锁 0、摄像机被读回 XYZ=0 区域。

### 修复①：锚点选定模型不再清空全部 XYZ 关键帧（只归零当前帧）

**成因**：v1.4.1 加入的「选中锚点目标后自动归零 XYZ 相对值」实现为 `resetXyzRelative()` 遍历 X / Y / Z 通道**全部关键帧**执行 `setValue(0)`——任何时刻选定模型都会把三轴通道里所有帧的相对偏移一并清零，后续播放时摄像机被拉回锚点（视觉上 ≈ 回到 XYZ=0 区域）。三个调用点（剪辑面板目标选择 / 部位切换 / 锚点帧工厂选人回调）都走该逻辑。

**现在**：`resetXyzRelative(clip, tick)` 只归零**当前播放头 tick** 处的关键帧值（该处无帧时补一个 0 值帧），其余帧的关键帧值一律保留不动——第 1 帧建好的关键帧不再被破坏，只有当前帧贴回锚点。

**实现**：`UIMultiTrackerClip.java`（新增 `cursorTick()` 与 tick 参数版 `resetXyzRelative` / `resetChannel`）+ `UIAnchorKeyframeFactoryMixin.java`（`bcp$wrapReset` 同步计算 tick 后传入）。

### 修复②：新建关键帧继承角度值归一化，不再"方位相同、数值天差地别"

**成因**：BBS `CameraController.getYaw()/getPitch()/getRoll()` 直接返回底层旋转角换算的度数，**没有值域归一化**（可超出 ±180°，如 -360 ~ 0 或更大范围）；而关键帧通道历史帧存的是标准 ±180 值域。删除偏航帧后重建，通道为空时继承值取到未归一化的脏角度 → 数值与历史帧差一整圈 → 插值 / 播放出现极高角度水平旋转。

**现在**：多样追踪的 `defaultInheritValue()` 对偏航 / 俯仰 / 横滚继承值统一**归一化到 (-180, 180]** 后再写入新帧，与通道历史值域一致；X / Y / Z 相对值与视野继承逻辑不变。

**实现**：`UIMultiTrackerClip.java`（`defaultInheritValue` 角度分支 + 新增 `normalizeAngle()`）。

### 修复③：连锁故障（新建剪辑选模型后 XYZ 锁 0 / 相机回原点）

**成因**：① + ② 的组合——新建剪辑用默认关键帧数值时，锚点选定模型触发了全通道归零（①），随后相机相对值被读回 0 区域。

**现在**：修复① 落地后连锁故障随之消失——选定模型只归零当前帧，其余帧的数值（含新建剪辑的默认帧）保留，摄像机不再被读回 XYZ=0。

### 修订（2026-10-10 当天二版）：空 XYZ 通道不再补 0 值帧，彻底杜绝"锁 0"

**实测复现**：一版修复后用户复测录屏（新建多样追踪剪辑 → 锚点选 GH 模型，XYZ 通道全程无关键帧），发现问题依旧。逐帧分析定位：一版修复的"当前 tick 处无帧则补一个 0 值帧"逻辑，在**新建剪辑空通道**场景下反而主动制造了 XYZ=0 关键帧——锚点选定模型的瞬间，空通道被写入 0 值帧，正是"XYZ 被强制锁定为零、摄像机被读回 XYZ=0 区域"的根源（与原有全部帧归零殊途同归）。

**现在**：`resetChannel()` 改为**仅当当前 tick 处已有关键帧时才将该帧值归零，绝不插入新帧**。空通道（新建剪辑未打 XYZ 帧）保持原状，XYZ 相对值继续走默认继承/剪辑属性，摄像机不会被拉回原点。

**实现**：`UIMultiTrackerClip.java`（`resetChannel` 删除 `channel.insert(tick, 0.0D)` 分支）。jar / sources 已重新构建并覆盖部署。

### 修订（2026-10-11）：XYZ 语义双模式——无锚点以绝对值为准、空通道不再飞回 0 0 0

**需求**：无 anchor（锚点）关键帧 / anchor 未绑定模型时，XYZ 以**绝对值**为主值，相对值（剪辑属性 `偏移 offset`）作为调试值（最终绝对值 = 绝对值 + 相对调试值）；anchor 绑定模型时以相对值为主（绝对值将被转化为相对值）。目的：避免删除关键帧后摄像机坐标飞回 0 0 0。

**现状确认**：多样追踪的播放逻辑中，未绑定锚点（`tracked=false`）时 XYZ 关键帧值本就是**绝对坐标**（新建帧继承逻辑 `相机坐标 - 锚点坐标`，无锚点时锚点=0 → 继承绝对坐标）；问题只在**关键帧通道为空**（删除全部帧）时，KeyframeClip 插值输出 0 → 相机飞回 0 0 0。

**现在**（`MultiTrackerClientClip.applyClip` 新增步骤 5，仅默认相对模式生效）：
* **无锚点 + 通道有帧**：最终位置 = 关键帧绝对坐标 + `偏移`（offset）作为**相对调试值**叠加（即需求公式「最终绝对值 = 绝对值 + 相对值」）；
* **无锚点 + 通道为空**（删除全部 XYZ 关键帧）：回退到**进入本剪辑前的相机位置**快照（`basePosition`），摄像机保持在上一步位置，不再跳回 0 0 0；
* **有锚点 + 通道为空**：维持原有行为（纯追踪锚点位置），不受影响；
* lookAt / 叠加模式不受影响（仅 `!additive && !lookAt` 路径生效）。

**实现**：`MultiTrackerClientClip.java`（applyClip 入口保存 `basePosition` + 步骤 5 分支）。jar / sources 已重新构建并覆盖部署。

### 修订（2026-10-11 三版）：角度双值——偏航/俯仰/横滚关键帧「调试 + 正式」

**需求**：垂直（俯仰）、水平（偏航）的角度值模式改为双值：**调试**（-360 ~ +360 度内值）、**正式**（不限，支持多圈角度）。示例：正式【361】⇄ 调试【1】；正式【-722】⇄ 调试【-2】（正式 = 圈数 × 360 + 调试，圈数自动换算）。

**现在**（新增 `UIAngleKeyframeFactory`，多样追踪剪辑的偏航 / 俯仰 / 横滚关键帧值面板改为双值联动）：
* **调试**：度内值（(-360, 360]，正式对 360 取余归一）。编辑调试 → 正式 = **当前圈数 × 360 + 新调试**（圈数保持不变，多圈旋转不受影响）；
* **正式**：不限（可直接输入 361、-722 等多圈角度）。编辑正式 → 直接写入关键帧通道，调试与圈数随之更新；
* 新建关键帧默认值仍走归一化继承（修复②成果保留：新帧从 0 圈开始，正式值在 ±180 内）。

**实现**：新增 `UIAngleKeyframeFactory.java`（axis yaw/pitch/roll）+ `BcpKeyframeFactories` 注册 `yaw/pitch/roll` + 中英语言 key（`angle_debug` / `angle_formal`）。jar / sources 已重新构建并覆盖部署。

## V1.5.3-Alpha（2026-10-10）

### 修复：与 BBS-Cubed 共存时，BCP 的「选择角色」显示样式优先生效

**成因**：玩家整合包同时装有 `BBS-Cubed-3.5.6+1.20.1.jar`（gbeic.bbsplusplus）。Cubed 同样 Mixin 接管了 `UIAnchorKeyframeFactory.displayActors`（滚动列表，条目显示为「key + formIdOrName」，即截图里的 `071cb8c1 - bbs:model`），且其注入先应用先执行，把本插件的「伪装名优先」菜单整个覆盖掉 —— 两个 mod 都有同功能修改时，显示跟了 Cubed。

**现在**：本插件 `UIAnchorKeyframeFactoryMixin` 的 Mixin priority 设为最低（0，默认 1000），注入在 Cubed 之后应用与执行，最终菜单由 BCP 接管，「伪装名优先」样式优先生效（有可辨识名直接显示名字；没有时「类型友好名 + 原 ID」兜底）。ID 串数据标识仍不动；Cubed 其他功能不受影响。

**实现**：`UIAnchorKeyframeFactoryMixin.java` 的 `@Mixin(value = UIAnchorKeyframeFactory.class, priority = 0)`。

### 修复：锚点「选择角色」列表显示名改为伪装名优先（不再被数据串替代）

**成因**：v1.0.3 的显示名方案把列表项拼成「ID 串 - formId - 伪装名」，未命名实体（如新添加的 `bbs:model`、`lumencore` 光源等）在列表里全显示成 `31ab03cd - bbs:model` 这类数据串，伪装名被压成后缀、甚至被数据串顶替，用户使用体验不佳。

**现在（显示名规则）**：

* 有可辨识名（优先级：自定义名 label → 表单名 form.name → 资产库同类型伪装名 → 影片内同类型演员名）→ **直接显示该名字**，不再带「ID 串 - formId」前缀；

* 确实没有可辨识名 → 「类型友好名 + 原 ID」兜底（如 `模型 31ab03cd`、`方块 605856a7`、`聚光灯 2b96e105`），不再满屏纯数据串。

**约束遵守**：

* ID 串作为 FS 核心数据标识**完全不动** —— 选择 / 存储的仍是 `Replay.getId()`，仅不再参与替代伪装名显示；

* 资产库（伪装）界面自身的**光标悬浮显示名**不受任何影响（名称反查仅发生在锚点列表内部，不回归集体覆盖 bug）。

**实现**：`UIAnchorKeyframeFactoryMixin` 的 `bcp$displayName` 重写 + 新增 `bcp$friendlyType` 类型友好名映射（`bbs:model`→模型 / `bbs:block`→方块 / `bbs:item`→物品 / `lumencore:spot_light`→聚光灯 / `lumencore:point_light`→点光源）。
