## V1.6.2（2026-10-20）【正式版・新增设置「关键帧展开模式」：默认（现状）/ 原始（一次性展开所有部件关键帧，排除被可视度筛选隐藏的轨道）】

### 新增：关键帧展开模式（设置 - 摄像机编辑设置 - 关键帧处理设置）

**背景**：BBS 2.7 更新后，动画编辑器（动画状态编辑器）打开 / 切换部件时，所有部件关键帧轨道默认折叠，不再像旧版那样一次性全部展开，需要手动逐个点出，非常麻烦。

  - **默认**：BBS 2.7 现状 —— 关键帧轨道折叠，需手动逐个点出展开；
  - **原始**：一次性展开**所有**部件关键帧轨道，恢复旧版（2.7 之前）行为；
- **可视度筛选联动**：被可视度筛选排除的轨道不会进入编辑器轨道列表，「原始」模式不会把它们展开（只展开可见轨道），避免误伤被隐藏的内容；

### 实现要点（不侵入原逻辑）

- 设置值沿用既有 `BcpModeValue`（单选值）+ `BcpModeValueUi`（说明文本 + 并列按钮，选中黄色高亮）通用链路，新增 key 为 `keyframe_expand`（`default` / `original`），默认 `default`；

## V1.5.4-Alpha（2026-10-13）【实验版・位置存储架构重构：每帧独立「游动 / 追踪」值】

> 用户在录屏实测中反馈：X / Z 坐标不再乱跑，但**所有 tick 下的 XYZ 轴继承模式是同步的**，游动与追踪的数据存储区用的是同一个，导致「从一地点追踪到伪装演员」时出现严重坐标偏差。
> 用户原话：**"这些功能的读取、继承用的几乎是同 1 个池子，需要每一个帧的所有值都需要再分出小类进行单独存储，避免出现相互污染的异常。"**

### 根源：剪辑级共享模式 + 单一 double 池

- **模式 clip 级共享**：原 `inheritMode / roamInheritMode / trackInheritMode` 是剪辑实例的 int 字段（不序列化），值面板按钮与播放端全部读写同一字段——任何 tick 切换模式，所有帧的语义同时改变。
- **游动 / 追踪值共用一个池**：原 x / y / z 每帧只存一个 Double，四值框本质是同一底层值 ± 锚点换算；游动段（绝对坐标）与追踪段（相对偏移）的编辑互相覆盖。

### 重构：新增帧级数据通道，每帧独立四值 + 两模式

- 新增数据类 `XyzFrameData`（每帧独立）：`roamValue`（游动世界坐标）、`trackRelative`（追踪相对锚点偏移）、`trackAbsolute`（追踪绝对世界坐标）、`roamMode / trackMode`（该帧各自的小模式）。
- 新增三个帧级通道 `xd / yd / zd`（`KeyframeChannel<XyzFrameData>`，工厂单例），构造中在锚点通道之后添加；旧的剪辑级共享模式字段**全部删除**。
- **值面板**：游动组（品红 0xFFFF6666）与追踪组（淡蓝 0x87CEFA）各有相对 / 绝对两个值框，均按当前帧独立存储；切换相对 / 绝对模式时按当前基准（游动用剪辑「偏移」调试值、追踪用当前 tick 锚点）相互转换，**世界坐标保持不变**。
- **打点继承**：在帧级通道打点时，空通道用当前摄像机视角构造（`roamValue = camera`、`trackRelative = camera − anchor`、`trackAbsolute = camera`）；有帧段取插值，不写 0、不锁 0。
- **锚点绑定变更**：只更新当前 tick 已存在的帧（贴回锚点：`roamValue = anchor`、`trackRelative = 0`、`trackAbsolute = anchor`），绝不新增帧、不影响其他帧。

### 游动 ⇄ 追踪过渡：不再瞬间跳转

- 播放端检测 anchor 相邻帧的路线状态（`<无>` ⇄ 绑定模型），不同则按段内进度对位置两端逐分量 lerp、角度两端走最短弧 lerp；追踪端单独解析其当前 tick 锚点位置（不与其他锚点帧混合），再与游动端混合——跨路线机位切换变为连续动画，而非瞬间跳转。
- **老存档兼容**：播放端优先读新帧级通道，空则回退父类旧 Double 通道（虚拟成 XyzFrameData），不打开编辑器直接播放也不丢机位、不崩。

**实现**：`client/data/XyzFrameData.java`、`client/data/XyzFrameDataKeyframeFactory.java`、`client/clips/MultiTrackerClientClip.java`、`client/ui/UIMultiTrackerClip.java`、`client/ui/UIXyzKeyframeFactory.java`、`client/ui/BcpKeyframeFactories.java`、`mixin/client/UIKeyframeDopeSheetMixin.java`。

## V1.5.4-Alpha（2026-10-10）【实验版・修复「多样追踪」三大相机关键帧异常】

> 用户在多样追踪剪辑实测录屏中反馈三个相互关联的异常：① 第 1 帧建好关键帧、第 10 帧新建锚点帧并选定模型后，XYZ 三轴关键帧被
>
> **全部强制归零**
>
> （不是当前帧，是所有）；② 删除偏航帧后重新新建帧，方位大致正确但
>
> **数值天差地别**
>
> ，播放时可能引发不明所以的极高角度水平视角切换；③ 两者结合的连锁故障：新建剪辑使用默认关键帧数值并选好模型后，XYZ 被强制锁 0、摄像机被读回 XYZ=0 区域。

### 修复①：锚点选定模型不再清空全部 XYZ 关键帧（只归零当前帧）

**成因**：v1.4.1 加入的「选中锚点目标后自动归零 XYZ 相对值」实现为 `resetXyzRelative()` 遍历 X / Y / Z 通道**全部关键帧**执行 `setValue(0)`—— 任何时刻选定模型都会把三轴通道里所有帧的相对偏移一并清零，后续播放时摄像机被拉回锚点（视觉上 ≈ 回到 XYZ=0 区域）。三个调用点（剪辑面板目标选择 / 部位切换 / 锚点帧工厂选人回调）都走该逻辑。

**现在**：`resetXyzRelative(clip, tick)` 只归零**当前播放头 tick** 处的关键帧值（该处无帧时补一个 0 值帧），其余帧的关键帧值一律保留不动 —— 第 1 帧建好的关键帧不再被破坏，只有当前帧贴回锚点。

**实现**：`UIMultiTrackerClip.java`（新增 `cursorTick()` 与 tick 参数版 `resetXyzRelative` / `resetChannel`）+ `UIAnchorKeyframeFactoryMixin.java`（`bcp$wrapReset` 同步计算 tick 后传入）。

### 修复②：新建关键帧继承角度值归一化，不再 "方位相同、数值天差地别"

**成因**：BBS `CameraController.getYaw()/getPitch()/getRoll()` 直接返回底层旋转角换算的度数，**没有值域归一化**（可超出 ±180°，如 -360 \~ 0 或更大范围）；而关键帧通道历史帧存的是标准 ±180 值域。删除偏航帧后重建，通道为空时继承值取到未归一化的脏角度 → 数值与历史帧差一整圈 → 插值 / 播放出现极高角度水平旋转。

**现在**：多样追踪的 `defaultInheritValue()` 对偏航 / 俯仰 / 横滚继承值统一**归一化到 (-180, 180]** 后再写入新帧，与通道历史值域一致；X / Y / Z 相对值与视野继承逻辑不变。

**实现**：`UIMultiTrackerClip.java`（`defaultInheritValue` 角度分支 + 新增 `normalizeAngle()`）。

### 修复③：连锁故障（新建剪辑选模型后 XYZ 锁 0 / 相机回原点）

**成因**：① + ② 的组合 —— 新建剪辑用默认关键帧数值时，锚点选定模型触发了全通道归零（①），随后相机相对值被读回 0 区域。

**现在**：修复① 落地后连锁故障随之消失 —— 选定模型只归零当前帧，其余帧的数值（含新建剪辑的默认帧）保留，摄像机不再被读回 XYZ=0。

### 修订（2026-10-10 当天二版）：空 XYZ 通道不再补 0 值帧，彻底杜绝 "锁 0"

**实测复现**：一版修复后用户复测录屏（新建多样追踪剪辑 → 锚点选 GH 模型，XYZ 通道全程无关键帧），发现问题依旧。逐帧分析定位：一版修复的 "当前 tick 处无帧则补一个 0 值帧" 逻辑，在**新建剪辑空通道**场景下反而主动制造了 XYZ=0 关键帧 —— 锚点选定模型的瞬间，空通道被写入 0 值帧，正是 "XYZ 被强制锁定为零、摄像机被读回 XYZ=0 区域" 的根源（与原有全部帧归零殊途同归）。

**现在**：`resetChannel()` 改为**仅当当前 tick 处已有关键帧时才将该帧值归零，绝不插入新帧**。空通道（新建剪辑未打 XYZ 帧）保持原状，XYZ 相对值继续走默认继承 / 剪辑属性，摄像机不会被拉回原点。

**实现**：`UIMultiTrackerClip.java`（`resetChannel` 删除 `channel.insert(tick, 0.0D)` 分支）。jar /sources 已重新构建并覆盖部署。

### 修订（2026-10-11）：XYZ 语义双模式 —— 无锚点以绝对值为准、空通道不再飞回 0 0 0

**需求**：无 anchor（锚点）关键帧 /anchor 未绑定模型时，XYZ 以**绝对值**为主值，相对值（剪辑属性 `偏移 offset`）作为调试值（最终绝对值 = 绝对值 + 相对调试值）；anchor 绑定模型时以相对值为主（绝对值将被转化为相对值）。目的：避免删除关键帧后摄像机坐标飞回 0 0 0。

**现状确认**：多样追踪的播放逻辑中，未绑定锚点（`tracked=false`）时 XYZ 关键帧值本就是**绝对坐标**（新建帧继承逻辑 `相机坐标 - 锚点坐标`，无锚点时锚点 = 0 → 继承绝对坐标）；问题只在**关键帧通道为空**（删除全部帧）时，KeyframeClip 插值输出 0 → 相机飞回 0 0 0。

**现在**（`MultiTrackerClientClip.applyClip` 新增步骤 5，仅默认相对模式生效）：



* **无锚点 + 通道有帧**：最终位置 = 关键帧绝对坐标 + `偏移`（offset）作为**相对调试值**叠加（即需求公式「最终绝对值 = 绝对值 + 相对值」）；

* **无锚点 + 通道为空**（删除全部 XYZ 关键帧）：回退到**进入本剪辑前的相机位置**快照（`basePosition`），摄像机保持在上一步位置，不再跳回 0 0 0；

* **有锚点 + 通道为空**：维持原有行为（纯追踪锚点位置），不受影响；

* lookAt / 叠加模式不受影响（仅 `!additive && !lookAt` 路径生效）。

**实现**：`MultiTrackerClientClip.java`（applyClip 入口保存 `basePosition` + 步骤 5 分支）。jar /sources 已重新构建并覆盖部署。

### 修订（2026-10-11 三版）：角度双值 —— 偏航 / 俯仰 / 横滚关键帧「调试 + 正式」

**需求**：垂直（俯仰）、水平（偏航）的角度值模式改为双值：**调试**（-360 \~ +360 度内值）、**正式**（不限，支持多圈角度）。示例：正式【361】⇄ 调试【1】；正式【-722】⇄ 调试【-2】（正式 = 圈数 × 360 + 调试，圈数自动换算）。

**现在**（新增 `UIAngleKeyframeFactory`，多样追踪剪辑的偏航 / 俯仰 / 横滚关键帧值面板改为双值联动）：



* **调试**：度内值（(-360, 360]，正式对 360 取余归一）。编辑调试 → 正式 = **当前圈数 × 360 + 新调试**（圈数保持不变，多圈旋转不受影响）；

### 修订（2026-10-11 四版）：「游动 / 追踪」双路线 —— 点击空白取消选中 + 跳视角彻底根治

**需求（用户复测反馈 + 结构调整）**：① 新建剪辑后点击空白区域无法取消选中关键帧；② XYZ 语义双模式仍未生效、跳视角依旧；③ 结构升级为双路线：默认新建一个空的 anchor 关键帧作为分派依据 —— anchor 未绑定<无>自动生效 **游动**（相对 / 绝对），anchor 绑定模型自动生效 **追踪**（相对 / 绝对）；两大模式各自内含两个小模式，游动与追踪的两组值互不串用，但每组内部相对 ⇄ 绝对仍可换算。

**修复①（点击空白取消选中）**：反编译确认原版 BBS 的取消路径（`pickOrStartSelectingKeyframes`）只对「graph 纯空白」生效；点击**轨道行内**空白会走 `clickSheets` 新建关键帧（且不走 BCP 的选中三模式注入、新帧直接选中），导致选中无法取消。**现在**在 `UIKeyframeDopeSheet.mouseClicked` 注入：左键点击「已选中关键帧所在轨道」的空白处 → 清空全部选中（内部同步关闭值面板）并拦截；无选中的轨道空白仍按原版打点，graph 纯空白仍走原版取消路径。

**修复②（跳视角根治）**：逐帧定位 `KeyframeChannel.interpolate` 在**播放头不在任何关键帧段**时返回 0（此前只修了「通道为空」回退，「有帧但播放头落在帧段外」仍被读成 0）—— 这正是删除/移动关键帧后相机与角度反复跳回原点的残留根源。**现在**全部取值改经 `safeValue()`：通道空 **或** 播放头无帧段 → 回退安全值，杜绝 0 值劫持。

**修复③（游动 / 追踪双路线，`applyClip` 按 anchor 绑定状态自动路由）**：

* **游动路线**（anchor 未绑定）：XYZ 关键帧存绝对坐标；**相对**（默认）= 播放再叠加 `偏移`（offset）相对调试值（最终 = 绝对 + 调试）；**绝对** = 播放直接用，offset 不参与。角度 / 视野空或无帧段 → 回退进入本剪辑前的值；
* **追踪路线**（anchor 绑定）：**相对**（默认）= 锚点 + 关键帧偏移（空 / 无帧段 = 纯追踪锚点）；**绝对** = 关键帧即绝对坐标（空 / 无帧段回退锚点）。角度空 / 无帧段 → 回退追踪角度（不再被读成 0）；

### 修订（2026-10-11 五版）：路线判定只看 anchor 关键帧值 —— 绑定伪装的帧正确显示「追踪」

**实测反馈**：四版后值面板按钮只有「游动·相对 / 游动·绝对」，绑定模型（伪装）的 anchor 帧也显示游动，看不到「追踪」按钮。

**成因**：四版 `isTracked` 判定需要「anchor 目标 → 影片实体列表 → 部位矩阵」**全部解析成功**才算追踪；用户绑定的伪装（资产库模型）不在影片演员实体列表中，实体解析失败 → 一律误判游动 —— 判定依据用错了（用了"能否求出锚点坐标"，而用户口径是"anchor 关键帧值是否为<无>"）。

**现在（判定口径修正）**：路线只看 **anchor 关键帧值** —— 值为 `<无>` → 游动；值**绑定模型 / 伪装**（`Anchor.hasTarget`）→ 追踪；anchor 通道完全无关键帧（老存档 / 手动删光）时才回落剪辑属性「目标」绑定（保持 v0.1 行为）。anchor 关键帧无论绑定伪装还是 `<无>` 都能正常进行视角动画。

* 值面板按钮随该 tick 的 anchor 值实时切换：绑定帧 → `追踪·相对 / 追踪·绝对`；`<无>` 帧 → `游动·相对 / 游动·绝对`；
* 播放求值同步用同一判定路由：绑定伪装但实体未实例化（锚点解析失败）时按「追踪」路线走、锚点视为 0（关键帧值即绝对坐标，角度 / 空通道回退进入前值）—— 不跳 0 0 0、不平视跳变，动画照常；
* 锚点感知归零 / 新建帧继承值同步改按新判定（绑定伪装解析失败时新帧存相机绝对坐标，播放一致不跳）。

**实现**：`UIMultiTrackerClip.java`（`isTracked` 改为 `hasTrackTarget` 按 anchor 关键帧值判定）+ `MultiTrackerClientClip.java`（applyClip 步骤 2 用 `hasTrackTarget` 门控路由，`trackResolved` 区分"锚点解析失败"回退进入前位置/角度）。jar /sources 已重新构建并覆盖部署。

**实测反馈（八版录屏）**：值面板出现布局抖动 / 重叠 —— 滚动到追踪组区域时，追踪组标题与下一行数值框重叠、两个数值文本相互黏连显示（如 `2.487532.203`）；面板滚动后分组标题缺失 / 错位。

**实现**：`UIXyzKeyframeFactory.java`（分组标题 + 4 数值框显式尺寸）。jar /sources 已重新构建并覆盖部署。

**成因**：玩家整合包同时装有 `BBS-Cubed-3.5.6+1.20.1.jar`（gbeic.bbsplusplus）。Cubed 同样 Mixin 接管了 `UIAnchorKeyframeFactory.displayActors`（滚动列表，条目显示为「key + formIdOrName」，即截图里的 `071cb8c1 - bbs:model`），且其注入先应用先执行，把本插件的「伪装名优先」菜单整个覆盖掉 —— 两个 mod 都有同功能修改时，显示跟了 Cubed。

**实现**：`UIAnchorKeyframeFactoryMixin.java` 的 `@Mixin(value = UIAnchorKeyframeFactory.class, priority = 0)`。

### 修复：锚点「选择角色」列表显示名改为伪装名优先（不再被数据串替代）

**成因**：v1.0.3 的显示名方案把列表项拼成「ID 串 - formId - 伪装名」，未命名实体（如新添加的 `bbs:model`、`lumencore` 光源等）在列表里全显示成 `31ab03cd - bbs:model` 这类数据串，伪装名被压成后缀、甚至被数据串顶替，用户使用体验不佳。

**现在（显示名规则）**：

* 有可辨识名（优先级：自定义名 label → 表单名 form.name → 资产库同类型伪装名 → 影片内同类型演员名）→ **直接显示该名字**，不再带「ID 串 - formId」前缀；

* 确实没有可辨识名 → 「类型友好名 + 原 ID」兜底（如 `模型 31ab03cd`、`方块 605856a7`、`聚光灯 2b96e105`），不再满屏纯数据串。

**约束遵守**：

* ID 串作为 FS 核心数据标识**完全不动** —— 选择 / 存储的仍是 `Replay.getId()`，仅不再参与替代伪装名显示；

* 资产库（伪装）界面自身的**光标悬浮显示名**不受任何影响（名称反查仅发生在锚点列表内部，不回归集体覆盖 bug）。

**实现**：`UIAnchorKeyframeFactoryMixin` 的 `bcp$displayName` 重写 + 新增 `bcp$friendlyType` 类型友好名映射（`bbs:model`→模型 / `bbs:block`→方块 / `bbs:item`→物品 / `lumencore:spot_light`→聚光灯 / `lumencore:point_light`→点光源）。
